4. Domain model, rules, objective (v1 spec)
Tables: plants, users, sessions, materials, material_specs, stock_formats, machines, parts, part_routings, rules_profiles, cut_jobs, job_events, plans, plan_sheets, placements, plan_metrics, plan_versions, exports, audit_log.
Generic model, no vertical leakage:
- materials — family name, dimension profile (1D/2D), attributes JSONB
- material_specs — thickness, surface/finish, grade, color — whatever the material needs (JSONB attributes + indexed core fields)
- stock_formats — nominal W×H (or length), cost, on-hand qty, quality flags, allowed machines
- parts — code, spec ref, finished dimensions, grain requirement, qty, rotate override, priority, source ref
- part_routings — operations → allowance (e.g. "grind: 2 mm/side", "edge delete: 1 mm"), ordered; cut size is computed, never typed
- rules_profiles — named reusable constraint set (below)
Rules profile fields (v1):
kerfMicron, trimPerEdgeMicron, allowRotate, grainMode (none/alongX/alongY), cutMode (guillotine/free), maxCutStages, minOffcutWMicron, minOffcutHMicron, minPartDimMicron, maxPartsPerSheet, edgeExclusionMicron, oversAllowedPct, machineLimits.
Objective (v1): ordered priority list chosen per job, default:
1. maximize priority-demand fulfilment (overs allowed within oversAllowedPct)
2. minimize sheets used
3. minimize unusable scrap area
4. minimize distinct patterns
5. minimize offcut count
Solution output: sheets[] (stock ref, placements, per-sheet stats), metrics (yield %, scrap/offcut/kerf/trim areas, sheets used, cost, elapsed), unplaced[], cutTree, warnings[], explanation{} (waste split, delta vs greedy baseline, binding constraint).
Solver interface (the seam that keeps everything future-proof):
type Solver interface {
    Name() string
    Capabilities() Capabilities           // 1D/2D, free/guillotine, polygons, rotation, grain
    Solve(ctx context.Context, p core.Problem, progress func(core.Solution)) (core.Solution, error)
}
Registration via a small registry keyed by capabilities, so adding pack3d or a CP-SAT sidecar later is a drop-in.
5. Solver strategy (pure Go, v1)
Build algorithm-first as a CLI spike before any web work — it's the only genuinely risky part.
Order	Component	What to implement
1	core + validator	Problem/Solution types, scoring, deterministic seed, invariants incl. guillotine cut-tree feasibility
2	pack1d	FFD/BFD baseline → DP knapsack pricing + column generation; leftover handling
3	pack2d	MaxRects/shelf baseline → guillotine beam search over cut trees → LP rounding + bin consolidation → local-search polish
4	cutter	Cut tree → operator steps; SVG/DXF/CSV writers
5	explain	Waste accounting, baseline comparison, binding-constraint notes
6	cmd/cutoptics bench	Runs ESICUP + internal instances, prints waste % table, fails CI on regression
Any-time behavior: the interface above reports best-so-far through progress; the API forwards it over SSE. Interactive budget 1–10 s, "night run" budget minutes. Same inputs + seed + solver version ⇒ byte-identical plan (store both on the plan row).
Quality bar: ≤200 parts in <5 s; waste within 5% of benchmark best-known on the golden set; zero invalid plans ever shown.

8. Quality gates (definition of done for anything solver-related)
1. Property tests (rapid): random instances → no overlap, in bounds, kerf/grain/trim respected, counts ≤ demand, guillotine cut tree valid.
2. Golden plans: fixed seed ⇒ identical output; changes to this file require an ADR note.
3. Fuzz parsers (CSV/DXF) and polygon/rect geometry.
4. Benchmark gate: bench fails CI if waste % on the golden set worsens >0.5%.
5. E2E: import → job → view → lock-edit → re-solve → export → accept.
6. Every plan carries solver_version + seed; UI always shows the greedy-baseline delta so "optimal-looking" plans are never oversold.
