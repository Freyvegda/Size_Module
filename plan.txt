# Size Module — Forward Plan (Phases 0–5)

Status snapshot and the next features to build. The cut-optimizer vertical slice
is mature: 2D/1D solvers + portfolios, guillotine validator, benchmark golden
gate, async queue with SSE, remnant lifecycle, plan editing with pinned
re-solve, CSV/SVG/DXF/PDF exports, costing + KPIs, campaigns and an assemblies
catalog.

Two facts drive this plan:

1. **The last five roadmap items are implemented but uncommitted.** `git log`
   shows a single "Initial commit"; the working tree carries ~40 modified and
   ~30 new paths. Building further on a dirty tree makes bisecting and the
   golden gate unreliable.
2. **Three seams are open** (confirmed in code); the assembly seam was closed
   by the per-material order flow. They are where the cheapest forward value
   lives.

| # | Seam | Evidence |
|---|---|---|
| 1 | Rules profiles are dead data: no API, jobs always use `core.DefaultRules()` | `rules_profiles` table + `cut_jobs.rules_profile_id` exist; no module reads them |
| 2 | ~~Assemblies never reach the optimizer~~ **addressed**: a product explodes per (material spec, dimension profile) and plans against that material's catalog stock, applying routing cut sizes | `frontend/src/features/optimizer/buildProblem.ts`, `ProductsPage.tsx` |
| 3 | Defect maps are engine-ready but unwired | `core.StockItem.Defects` honored in shelf/beam/maxrects/improve/pinned; zero `defect` in `db/` or `modules/` |
| 4 | `MaxCutStages` is declared, never enforced | `core/types.go:143`, no other reader |

Effort is relative: **S** ≈ 1–2 days, **M** ≈ 3–5, **L** ≈ 1–2 weeks, **XL** > 2 weeks.

---

## Guardrails (apply to every phase)

- **Units**: every length is integer micrometers (`int64`) in DB, API and solver.
  Floats only for cost, percent, m². Convert at the UI edge (`lib/format.ts`).
- **One solver seam**: new algorithms implement `core.Solver` and are
  registered; never branch on a solver in callers.
- **Validate before you show or store**: every solution passes
  `validator.Validate`, including guillotine cut-tree feasibility.
- **Determinism**: same problem + seed + solver version ⇒ identical plan.
- **Generated code**: `db/queries/*.sql` → `db/scripts/generate.ps1`; never
  hand-edit `backend/internal/platform/db/*`.
- **Contract sync**: every new endpoint gets an `api/openapi.yaml` entry; until
  Phase 2 (C2) `frontend/src/lib/types.ts` is still hand-synced.
- **Golden gate**: solver-affecting changes must pass
  `go test ./...` / `bench -check` (mean score may not drop > 0.5 points).

## Phase 1 — Close the seams (Track A) · highest ROI

### A1. Rules profiles + objective presets · **M**

Unlocks per-material machine settings (glass vs wood kerf/trim/grain/cut mode)
and cost-vs-yield objective presets. Today a caller must send a whole rules
object to change anything.

- **DB**: reuse `rules_profiles`; add `db/queries/rules_profiles.sql`
  (list/get/create/update/delete) → `generate.ps1`.
- **Backend**: new `internal/modules/rules/` module; resolve
  `?rulesProfileId=` in `jobs/http.go` (both `/optimize` and `/jobs`) and on
  campaign create, then feed it into `core.Normalize`. Keep the request-body
  rules as an override.
- **Frontend**: `/rules` page + editor; profile picker on the Jobs page and the
  campaign create form. Replaces the current "send the complete default rules
  object for free mode" workaround.
- **Accept**: a glass profile (guillotine, 4 mm kerf, grain alongY) and a wood
  profile (different trim and offcut policy) both round-trip and visibly change
  a solve.

### A2. Assembly BOM → job · **M**

Makes the product catalog load-bearing instead of display-only.

- **Backend**: `POST /api/v1/assemblies/{id}/explode` returning parts +
  quantities; cut size = component finished size + allowances from its material
  spec/routing. Optional `POST …/to-job` that submits directly.
- **Decision (default)**: assemblies may mix 1D beams and 2D panels, but a
  `core.Problem` is single-profile (`DetectProfile` picks 2D if any 2D part).
  The explosion **splits into one job per dimension profile / material spec**.
- **Frontend**: "Send to optimizer" action on `ProductsPage`.
- **Accept**: the seeded window (glass panels + frame beams) produces two jobs,
  each solvable and archived.

### A3. Defect maps · **M**

Strong differentiator for wood (knots, splits) and flawed glass, and the engine
already respects defects — only plumbing and UI are missing.

- **DB**: migration `0007_stock_defects.sql` adding
  `stock_items.defects JSONB NOT NULL DEFAULT '[]'`; extend `stock_items.sql`
  and the `ListRemnants` / `SaveRun` mappings so core stock carries defects.
- **Backend**: add defects to `stock.Item`, `CreateInput`, `UpdateInput` with a
  rectangle validator; **add a defect check to `validator.Validate`** so a
  defect-aware plan can never bypass the gate.
- **Frontend**: draw defect regions in `PlanScene.tsx`; add a simple rectangle
  editor on the Stock page.
- **Accept**: a remnant with a central defect places no piece over it and passes
  validation.

### A4. Enforce `maxCutStages` · **S**

- **Backend**: give `geom.BuildCutTree` a stage/depth result, constrain beam
  child generation, and enforce in `validator`. Keep shelf's implicit 2-stage
  guarantee as a regression test.
- **Accept**: `maxCutStages: 2` yields a valid staged plan or a violation;
  covered by a property test.

## Phase 2 — Platform hardening (Track C, part 1) · before the surface grows

### C1. Auth + sessions + RBAC · **L**

`users.role` and `users.password_hash` exist; there is no auth module and no
sessions table. `audit_log` is already written by acceptance.

- **DB**: add `sessions` (or go stateless JWT — see decisions).
- **Backend**: `internal/modules/identity` (login/logout/me), chi middleware,
  role gates (`admin | planner | operator | viewer`) on mutations
  (create/accept/edit/reoptimize).
- **Frontend**: login route, token attach in `lib/api.ts`, route guard in
  `App.tsx`, user menu and role-aware actions.
- **Accept**: a viewer cannot accept or edit a plan (403); an operator cannot
  manage users.

### C2. OpenAPI codegen + drift check · **M**

`frontend/src/lib/types.ts` ↔ `backend/api/openapi.yaml` is hand-synced and
called out as a classic bug source.

- **Plan**: complete `openapi.yaml` for all current endpoints; generate
  `types.ts` with `openapi-typescript`; add a pnpm script and a CI job
  (`generate && git diff --exit-code`). Keep Go handlers hand-written; if Go
  drift coverage is wanted, generate request/response types into a separate
  package rather than replacing `core`.
- **Accept**: editing the spec without regenerating fails CI.

## Cross-cutting quality gates

1. **Runtime correctness** — `validator.Validate` on every solve (extended in
   A3/A4 for defects and cut stages).
2. **Benchmark gate** — `golden.json` + `bench -check` / `TestGoldenGate`;
   `bench -update` only with a committed rationale.
3. **Invariant tests** — unit/property tests per package; postgres integration
   tests for edit → lock → re-solve → accept and for new DB features.
4. **Contract tests** — `openapi.yaml` in sync with handlers (C2).
5. **E2E** — import → job → view → lock-edit → re-solve → export → accept (C5).

---

## Open decisions (recommended defaults; change if you disagree)

1. **Assembly explosion**: split mixed assemblies into per-profile jobs
   **(default)**, or reject mixed and require one profile per assembly.
2. **Auth**: local `sessions` table **(default: simpler revocation, no key
   management)** vs stateless JWT.
3. **Codegen scope**: TS types only **(default: fast, low churn)** vs also
   generated Go DTOs.
4. **Defect authoring**: UI rectangle editor on the Stock page **(default)**
   plus API/CSV for bulk.
